# Investigation: Autosave Memory Context Poisoning

> **Parent investigation:** `.kilo/plans/1775420927163-eager-river.md` (Section 12: Cron Job Context Duplication Cascade, Section 10: Recommended Remediation Priorities #5)
> **Status:** Fix planned (not yet implemented)

---

## Core Root Cause

**The bug lives in a core shared module:** `src/memory/mod.rs:106-117` — `should_skip_autosave_content()`.

This filter is the single guard function used by **every autosave call site** in the codebase. It determines whether content should be blocked from being persisted to memory. The filter was designed to drop synthetic noise (cron headers, heartbeat tasks, distilled indices) but has a critical gap:

**It does NOT block content starting with `[Memory context]`.**

Since `[Memory context]` blocks are synthetic, system-generated context preambles (not real user conversation), they should never be persisted as autosave entries. But because they pass this filter, any enriched message containing recalled memory context can leak into the memory store.

### All Affected Autosave Call Sites

| Call Site | File:Line | What Gets Saved |
|-----------|-----------|-----------------|
| CLI single-shot | `loop_.rs:3898-3911` | `effective_msg` (user input or prefixed prompt) |
| CLI interactive | `loop_.rs:4176-4189` | `effective_input` (typed input) |
| Channel daemon | `channels/mod.rs:2583-2597` | `msg.content` (raw channel message) |
| Gateway webhooks | `gateway/mod.rs:1435,1668,1787,1902,2019` | `msg.content` (webhook payload) |
| Cron/daemon via `run()` | `cron/scheduler.rs:307 → loop_.rs:3898` | `prefixed_prompt` (includes recalled `[Memory context]`) |

**Every path uses the same guard:** `!memory::should_skip_autosave_content(&content)`. The filter gap is systemic, not cron-specific.

## Problem: Recursive Memory Poisoning

The autosave pipeline recursively poisons memory entries with nested `[Memory context]` blocks, causing exponential nesting over time.

**Most visible manifestation — Cron Job Context Duplication Cascade (detailed example):**

A cron job with `prompt: "try invoking the cron job 'Daily Morning Briefing (Hebrew)'"` caused the same ~78-line cron instruction block to repeat ~15–20+ times in the LLM call, resulting in 7528-line context dumps.

**How the poisoning chain plays out (cron vector):**

**Layer 1: Double-injection** — scheduler recalls memories → prepends `[Memory context]`, then `agent::run()` recalls again via `build_context()` → same entries appear twice

**Layer 2: Recursive poisoning** — entries containing `[Memory context]` literal text get auto-saved (filter gap!), recalled, expanded, and re-saved exponentially

**Layer 3: LLM hallucination loop** — context bloat causes the LLM to repeat instructions in responses, which get saved and recalled again

### Root Cause Chain (cron manifestation)

1. User runs: `try invoking the cron job "Daily Morning Briefing (Hebrew)"`
2. `scheduler.rs:283-302` recalls memories → prepends `[Memory context]\n- entries\n\n[cron:N job] prompt`
3. `run()` receives prefixed prompt → `should_skip_autosave_content` checks `starts_with("[cron:")` → BUT the string starts with `[Memory context]` first → **filter PASSES** → full poisoned content autosaved
4. Next cron run recalls the poisoned entry → nested `[Memory context]` + cron instructions in `prefixed_prompt`
5. Agent turn recalls AGAIN → another `[Memory context]` nested inside
6. LLM echoes cron instructions (context bloat confusion) → response saved → exponential growth

### Code-Level Root Cause

In `src/cron/scheduler.rs:283-302`:
```rust
format!("[Memory context]\n{ctx}\n\n[cron:{} {name}] {prompt}", job.id)
```

In `src/memory/mod.rs:106-117`:
```rust
let lowered = normalized.to_ascii_lowercase();
lowered.starts_with("[cron:")  // ❌ Only checks this — misses [Memory context]
    || lowered.starts_with("[heartbeat task")
    || lowered.starts_with("[distilled_")
    || lowered.contains("distilled_index_sig:")
```

The poisoned prompt starts with `[Memory context]\n`, not `[cron:`, so the check passes and the full content (including nested memory entries) gets autosaved via `src/agent/loop_.rs:3898-3911`.

### Where the Scheduler and Agent Both Recall
```
scheduler.rs:run_agent_job()
  ├── mem.recall(&prompt, 5, ...)         → "[Memory context]\n..."
  └── agent::run(Some(prefixed_prompt))
       └── loop_.rs:3915-3932
            └── build_context(mem, &effective_msg, ...) → another "\n[Memory context]\n..."
```

**Key code in `src/agent/loop_.rs:3915–3932`:**
```rust
let mem_context = build_context(
    mem.as_ref(),
    &effective_msg,
    config.memory.min_relevance_score,
    memory_session_id.as_deref(),
)
.await;
```

This recalls memories based on `effective_msg` — which for cron jobs contains the full `[cron:...]` instructions. The scheduler already recalled and prepended `[Memory context]`, so this call injects a duplicate set.

### Filter Gaps

| Filter | What It Blocks | Gap |
|--------|---------------|-----|
| `should_skip_autosave_content` (CORE GAP) | `[cron:`, `[heartbeat task`, `[distilled_` | Does NOT block `[Memory context]` literal content |
| `is_assistant_autosave_key` | `assistant_resp*` keys | Does NOT block `user_msg*` keys with nested context |
| `should_skip_memory_context_entry` (inject-time) | `_history` keys, `[IMAGE:`, `<tool_result` | Does NOT block entries whose content IS literally `"[Memory context]"` |

### Critical Finding: `process_message()` Does NOT Autosave

The `process_message()` function (loop_.rs ~4454+) does NOT call `autosave_memory_key` or `mem.store()` for user/assistant messages. It only builds enriched context and calls `agent_turn()`. This means the poisoning vector is exclusively through `run()` (CLI single-shot, CLI interactive, and cron/daemon calls), NOT through every REPL turn.

### What Content Actually Flows into Autosave

In all autosave call sites, the content being saved is the RAW user input (after thinking directive parsing):
- `effective_msg` (loop_.rs:3907) — raw user message
- `effective_input` (loop_.rs:4185) — raw typed input
- `msg.content` (channels/mod.rs:2592) — raw channel message
- Gateway payloads — raw webhook content

**No autosave call site saves the enriched/enriched user message** containing `[Memory context]`. The enriched message is only passed to the LLM via chat history. **But** the cron path bypasses this by passing the prefixed prompt (which already contains `[Memory context]`) directly to `run()`, where it IS autosaved as the raw input.

### Memory Storage (WRITE Path)

Both storage backends write key and content directly without additional filtering (filtering happens before `store()` is called):
- **SQLite**: `src/memory/sqlite.rs:564` — `async fn store(...)` inserts into SQLite with embeddings
- **Markdown**: `src/memory/markdown.rs:144` — `async fn store(...)` appends to MEMORY.md. Core entries (category=Core) are appended here with no deletion possible — `forget()` always returns `false` (`src/memory/markdown.rs:254-258`).

### Key Format: Why Poisoned Entries Bypass `is_assistant_autosave_key`

`autosave_memory_key` (`loop_.rs:299`) generates keys as:
```rust
format!("{prefix}_{}", Uuid::new_v4())
```

Poisoned entries get keys like `user_msg_b3a0e7c2-...` — these match the `user_msg_*` pattern, NOT `assistant_resp*`. The `is_assistant_autosave_key` filter only blocks `assistant_resp` and `assistant_resp_*` keys, so all poisoned entries pass through as if they were legitimate user conversation messages.

### Inject-Time Filter: `should_skip_memory_context_entry` (channels only)

`channels/mod.rs:1354-1384` — `should_skip_memory_context_entry(key, content)` is an additional filter used when building memory context for injection into channel messages. It checks:

1. `memory::is_assistant_autosave_key(key)` — blocks `assistant_resp*` keys
2. `memory::should_skip_autosave_content(content)` — blocks cron/heartbeat/distilled patterns
3. `key.trim().to_ascii_lowercase().ends_with("_history")` — blocks history entries
4. `content.contains("[IMAGE:")` — blocks image markers (prevents duplicate image blocks)
5. `content.contains("<tool_result")` — blocks orphan tool results
6. `content.chars().count() > MEMORY_CONTEXT_MAX_CHARS` — blocks oversize entries

**Gap:** Does NOT block entries whose content IS literally `"[Memory context]\n- ..."` — none of the above checks catch it.

### Verdict

Memory context content CAN end up in saved memory entries through this specific code path:

1. Cron scheduler in `cron/scheduler.rs:282-302` recalls memories and prepends `[Memory context]...` to the prompt
2. The prefixed prompt is sent to `crate::agent::run()` at line 307
3. In `loop_.rs:3898-3911`, `should_skip_autosave_content(&effective_msg)` checks `starts_with("[cron:")` but the string starts with `[Memory context]` first → **the check does NOT skip**
4. The full string (including `[Memory context]` with nested memory entries) is saved via `mem.store(&user_key, &effective_msg, ...)`
5. On the next cron run, these poisoned entries are recalled again, causing exponential nesting

## Fix Plan

### Recommended Fixes (from parent investigation, Section 12)

1. **Block `[Memory context]` content from autosave** — Add to `should_skip_autosave_content()`:
   ```rust
   lowered.starts_with("[memory context]")
   ```
2. **Skip second memory recall for cron/daemon messages** — In `loop_.rs`, detect if `effective_msg` already contains `[cron:` prefix and skip `build_context()` (memory already recalled by scheduler/daemon caller)
3. **Add recency-based dedup to recall** — If a memory entry's content already appears in the conversation history or system prompt prefix, skip injection
4. **Cap `effective_msg` length before `build_context()`** — If the cron prompt is >4K chars, it's clearly a job definition not a query; use a short summary for recall instead

### 1. Update `should_skip_autosave_content` (src/memory/mod.rs:106-117)

This implements fix #1 above.

Add `lowered.starts_with("[memory context]") ||` to the filter chain.

```rust
pub fn should_skip_autosave_content(content: &str) -> bool {
    let normalized = content.trim();
    if normalized.is_empty() {
        return true;
    }

    let lowered = normalized.to_ascii_lowercase();
    lowered.starts_with("[cron:")
        || lowered.starts_with("[heartbeat task")
        || lowered.starts_with("[distilled_")
        || lowered.contains("distilled_index_sig:")
        || lowered.starts_with("[memory context]")
}
```

### 2. Add test for the new filter pattern

Test that content starting with `[Memory context]` is correctly skipped.

- **Risk**: Low — purely additive filter, prevents saving synthetic context blocks

- **Side effects**: None — `[Memory context]` is a synthetic system block that should never be stored as user memory
