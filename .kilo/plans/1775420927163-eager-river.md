- Worst case: 20K chars of ancient memories in system prompt, latest 100 entries lost

## 5. DateTime Injection Breaking Prompt Caching — Completed

### The Problem
The DateTime section injects a **second-precision timestamp** into the system prompt, completely preventing server-side prompt caching.

### Evidence

**Two DateTime injection points (both second-precision):**

1. `src/agent/prompt.rs:260–282` — `DateTimeSection::build()`
   - Format: `Date: YYYY-MM-DD | Time: HH:MM:SS (TZ) | ISO 8601: YYYY-MM-DDTHH:MM:SS±HH:MM`
   
2. `src/channels/mod.rs:3988–3995` — inline builder
   - Format: `YYYY-MM-DD HH:MM:SS (TZ)`

**Anthropic prompt caching infrastructure exists but is completely ineffective:**

- `src/providers/anthropic.rs:87–144` — `CacheControl` enum with `ephemeral` type
- `src/providers/anthropic.rs:496–501` — applies `cache_control: Some(CacheControl::ephemeral())` to ALL system blocks
- `src/providers/traits.rs:283–285` — `ProviderCapabilities::prompt_caching` capability flag
- `src/providers/anthropic.rs:884` — Anthropic advertises `prompt_caching: true`

### Impact
- Anthropic caches based on prompt content hash
- Since DateTime changes every **second**, system prompt hash differs every request
- **Cache hit rate: effectively 0%**
- Full price per turn instead of ~10x cheaper cached pricing
- For ~30K prompt: ~$0.15–$0.30 waste vs ~$0.015 cached

### Resolution Options

1. **Option A: Move DateTime to user message** (Recommended) — inject timestamp as first user message, keeping system prompt fully static and cacheable
2. **Option B: Split system blocks** — Anthropic supports multiple system blocks; cache static ones separately from DateTime block
3. **Option C: Reduce precision to hourly** — `YYYY-MM-DD HH:00:00` changes only hourly, partial cache reuse
4. **Option D: Remove seconds** — `YYYY-MM-DD HH:MM` changes only minutely, still breaks caching but less aggressively

### RuntimeSection Note
`src/agent/prompt.rs:245–257` — `RuntimeSection` injects host OS, model name. Less volatile (static per session) but should be verified as cacheable.

## 12. Cron Job Context Duplication Cascade — Completed

### The Problem
A cron job with `prompt: "try invoking the cron job 'Daily Morning Briefing (Hebrew)'"` caused the same ~78-line cron instruction block to repeat ~15–20+ times in the LLM call, resulting in 7528-line context dumps.

### Duplication Cascade

**Layer 1: Scheduler → Agent memory recall double-injection**
- `src/cron/scheduler.rs:283–302` — scheduler recalls memories and prepends `[Memory context]\n...\n\n` to the cron prompt
- Then `agent::run()` (single-shot path, `src/agent/loop_.rs:3915–3932`) recalls memories AGAIN via `build_context()` and injects them into the enriched user message
- Result: same memory entries appear **twice** in the request — once in system-prefix, once in user message

**Layer 2: Recursive memory poisoning**
- Memory entries like `user_msg: try invoking the cron job "Daily Morning Briefing (Hebrew)"` get auto-saved (it does NOT start with `[cron:`)
- Memory entries like `user_msg_dc3179f2-05cb-40ab-b1e7-832f68ba0ad9: [Memory context]` — content is LITERAL `"[Memory context]"` string — stored by a previous run's enriched message containing recalled context
- Each cron run recalls these poisoned entries, expanding the `[Memory context]` blob exponentially (each iteration nests the previous run's memory context inside a new one)

**Layer 3: LLM hallucination loop**
- When context bloat causes the LLM to lose track, it starts repeating the cron instructions in its own responses
- Responses get auto-saved (if > `AUTOSAVE_MIN_MESSAGE_CHARS` and not blocked by `should_skip_autosave_content`)
- Next recall surfaces these hallucinated repetitions, compounding the duplication

### Where the Scheduler and Agent Both Recall

```
scheduler.rs:run_agent_job()
  ├── mem.recall(&prompt, 5, ...)         → "[Memory context]\n..."
  └── agent::run(Some(prefixed_prompt))
       └── loop_.rs:3915-3932
            └── build_context(mem, &effective_msg, ...) → another "\n[Memory context]\n..."
```

**Key code in `src/agent/loop_.rs:3915–3932`:**
```rust
let mem_context = build_context(
    mem.as_ref(),
    &effective_msg,
    config.memory.min_relevance_score,
    memory_session_id.as_deref(),
)
.await;
```

This recalls memories based on `effective_msg` — which for cron jobs contains the full `[cron:...]` instructions.

### Filter Gaps

| Filter | What It Blocks | Gap |
|--------|---------------|-----|
| `should_skip_autosave_content` | `[cron:`, `[heartbeat task`, `[distilled_` | Does NOT block `[Memory context]` literal content |
| `is_assistant_autosave_key` | `assistant_resp*` keys | Does NOT block `user_msg*` keys with nested context |
| `should_skip_memory_context_entry` (inject-time) | `_history` keys, `[IMAGE:`, `<tool_result` | Does NOT block entries whose content IS literally `"[Memory context]"` |

### Root Cause Chain
1. User runs: `try invoking the cron job "Daily Morning Briefing (Hebrew)"`
2. Agent auto-saves: `user_msg_abc123: [Memory context]\n- ...entries...\n\n[cron:xxx ...]` to MEMORY.md/SQLite
3. Next cron run: scheduler recalls this entry → the `[Memory context]` + cron instructions appear in `prefixed_prompt`
4. Agent turn ALSO recalls → another `[Memory context]` nested inside
5. The LLM response echoes the cron instructions back (confusion from context bloat)
6. Response gets saved → recalled again next time → exponential growth

### Recommended Fixes

1. **Block `[Memory context]` content from autosave** — Add to `should_skip_autosave_content()`:
   ```rust
   lowered.starts_with("[memory context]")
   ```
2. **Skip second memory recall for cron/daemon messages** — In `loop_.rs`, detect if `effective_msg` already contains `[cron:` prefix and skip `build_context()` (memory already recalled by scheduler/daemon caller)
3. **Add recency-based dedup to recall** — If a memory entry's content already appears in the conversation history or system prompt prefix, skip injection
4. **Cap `effective_msg` length before `build_context()`** — If the cron prompt is >4K chars, it's clearly a job definition not a query; use a short summary for recall instead

## 11. Tool Injection Bloat — Completed

### The Problem
Tools are injected **twice** into the system prompt for every turn, with full JSON schemas in the non-native path.

### Two Injection Points (Non-Native Path)

**Point 1: Tool Descriptions in `build_system_prompt_with_mode_and_autonomy`**
- `src/agent/loop_.rs:3700–3816` builds `tool_descs: Vec<(&str, &str)>` — ~40+ hardcoded tool name+description pairs
- `src/channels/mod.rs:3848–3863` injects them as `- **{name}**: {desc}` list
- With `compact_context: true`: reduced to `Available tools: shell, file_read, file_write, ...` (names only)
- With `compact_context: false` (default): full name + description for every tool

**Point 2: Full JSON Schemas in `build_tool_instructions`**
- `src/agent/loop_.rs:3838–3840` — only when `!native_tools`
- `src/agent/loop_.rs:3423–3454` — `build_tool_instructions()` iterates `tools_registry`
- Every tool gets: **name + description + entire JSON schema** via `tool.parameters_schema()`
- For ~30+ tools: ~15K–30K chars of JSON schemas every turn
- **No compact mode exists** for this path — always full schemas

### Current Mitigations (Partial)
| Mechanism | What It Does | Gap |
|-----------|-------------|-----|
| `compact_context` | Reduces tool descriptions to names only in Point 1 | Does NOT affect Point 2 (JSON schemas) |
| `--allowed-tools` CLI flag | Restricts registry to allowlist (`src/agent/loop_.rs:3547–3549`) | Requires manual config, not automatic |
| MCP deferred loading | Only names injected, schemas on-demand via `tool_search` (`src/tools/mcp_deferred.rs:230`) | Only applies to MCP tools, not built-in tools |
| `compute_excluded_mcp_tools()` | Per-turn MCP tool exclusion (`src/agent/loop_.rs:3948–3953`) | MCP only |

### What Gets Injected (Non-Native, Non-Compact Mode)
1. `tool_descs` — ~40 tool name+description pairs (markdown list)
2. `build_tool_instructions` — ~30+ tools × (name + description + JSON schema) = ~15K–30K chars
3. MCP deferred tools — names only (good)

**Total tool bloat per turn: ~20K–40K chars (~5K–10K tokens) for ~30+ built-in tools

### Resolution Options

1. **Option A: Add Compact mode to `build_tool_instructions`** (Recommended — Low Risk)
   - Add `compact: bool` parameter to `build_tool_instructions`
   - When compact: inject only `## Available Tools\n\n- **{name}**: {desc}` for each tool
   - Skip JSON schemas entirely; LLM can infer parameters from descriptions
   - Already have `compact_context` flag available — thread it through

2. **Option B: Deferred tool schema loading for built-in tools**
   - Mirror MCP deferred pattern for built-in tools
   - Inject names only, add `get_tool_schema(name)` tool for on-demand lookup
   - Higher risk, more complex, but eliminates tool bloat entirely

3. **Option C: Tool relevance prefilter**
   - Score tools against user message content before injection
   - Only inject tools with relevance score > threshold
   - Medium complexity, risk of missing relevant tools

4. **Option D: Compress JSON schemas**
   - Strip redundant fields (descriptions already in tool_descs, don't repeat)
   - Remove nested descriptions, enums with obvious values
   - Medium impact, keeps schemas but reduces size ~50%

### Recommended: Option A
Simplest, most effective change. Thread `compact_context` (which already defaults to `true` in config at `src/config/schema.rs:1308`) through to `build_tool_instructions`. When compact, skip JSON schemas — inject only names and descriptions. LLM already knows how to call tools from the protocol instructions; parameter hints can be derived from descriptions.
